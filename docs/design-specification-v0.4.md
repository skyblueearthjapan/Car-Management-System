# 車両管理予約システム 設計仕様書（v0.4）

## 概要

v0.3からの確定事項：
- **午前：08:00–13:00 / 午後：13:00–18:00**
- **複数日予約：OK**（デフォは一括適用）
- **ユーザー紐付け（UserMap/UserMSP等）は使わない**
- **予約者は毎回 部署→氏名の選択式**
- **保存：直感的UI＋将来自動保存。ただし確実に保存できる方式（競合チェック込み）**

---

## 1. 予約ルール v0.4（確定）

### 1-1. スロット定義（固定）

| スロット | 時間帯 |
|----------|--------|
| AM | 08:00–13:00 |
| PM | 13:00–18:00 |
| FULL | 08:00–18:00（社内運用上の"終日"） |

### 1-2. 時間指定（任意・深い階層）

- 時間指定は可能。ただし"階層深くてOK"
- ルール：
  - **AM 内**なら 08:00–13:00 の範囲で指定
  - **PM 内**なら 13:00–18:00 の範囲で指定
  - **FULL** は 08:00–18:00 内で指定（または指定なし）
- **競合判定**は時間指定がある場合は時間重なり、ない場合はスロット占有で判定

## 4. 保存方式（重要：直感的UI＋将来自動保存、でも確実に保存）

「ユーザーの煩わしさを削る」要求が強いので、**二段構え**が一番安全。

### 4-1. MVPで採用する保存方式（確実優先）

- 予約操作（追加/変更/取消）のたびに**即時サーバ保存**
- UI的には「保存ボタンを押す」というより：
  - クリック→モーダル→確定 でその場保存
- **保存成功時**: トースト「保存しました」＋画面反映
- **保存失敗（競合）時**: トースト＋当該車両/日を強調して再読み込み誘導

> **メリット**: "保存し忘れ" が起きないので、運用が安定

### 4-2. 自動保存（将来実装の方針）

日別詳細編集（複数日をいじる画面）など「編集量が多い箇所」だけ：
- クライアント側に draft を持つ
- 一定時間無操作（例 2秒）で自動保存
- 画面右上に保存状態表示：`保存中…` → `保存済み`
- ただし自動保存でも、最後はサーバ側で競合チェックして確実性担保

**結論**: 「全操作即時保存」＋「編集が多い箇所は自動保存」＝煩わしさと確実性の両立

---

## 5. 競合チェック（サーバ側で確定）

保存時に Apps Script 側で必ず実施：

### 排他制御
- `LockService` で排他

### 競合条件
- 同一 `vehicle_id`、同一 `date`、スロット/時間帯の重なり
- FULL は AM/PM と常に競合
- 時間指定がある場合は時間帯重なりで判定

### エラー返却（UIで扱いやすく）

```javascript
{
  code: "CONFLICT",
  conflicts: [
    {
      vehicle_id: "V0001",
      date: "2026-01-23",
      slot: "AM",
      existing_dept: "営業部",
      existing_name: "山田太郎",
      existing_time_range: "08:00-13:00"
    }
  ]
}
```

→ 「〇〇（部署/氏名）が既に予約しています」と表示できる
